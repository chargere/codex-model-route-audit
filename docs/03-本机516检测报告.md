生成时间：2026-11-08　范围：`~/.codex/sessions/` 全部 25 个会话（10/28–11/07），只读统计，不提取任何对话文本。

## 一句话结论

**第三种成因（系统指令层导致的 reasoning 预算截断）在你本机日志里几乎不成立**：1405 次响应中只有 7 次落在 `516 + n×518` 的固定块边界，占 0.5%（占 `>=516` 响应的 6.0%），而社区 5 月 GPT-5.5 高峰期的同口径是 44.0%。你正在做的冷号方向没有被这份数据推翻。

但有个必须说清的局限：**本地日志只记录「客户端设定的模型」，测不了服务端静默换模型**。日志里 `gpt-6-luna` 有 765 次响应，看着吓人，但 11/03 一个会话里在 astra/luna/sol/terra 之间切了 20 次，明显是手动对比测试，不是被静默路由过去的。

## 二、第三种成因到底是什么

不是「模型变笨」，也不是「换了小模型」，而是**推理预算被按固定大小的块切开，中途被掐断**。四份独立材料拼出的链条：

### 1. 触发开关：内置指令让模型预判「这题简单吗」

linux.do 1701975 帖 340 楼（shinorochi, 5/24）挖出 ChatGPT 内置开发者指令 `<user_updates_spec>`：要求每 15 秒或 2-3 次工具调用发一次 `commentary` 进度更新，并且 VERY IMPORTANT 要求**任务刚到达就按「>10 秒 / 多步 / 多次工具调用」私下预判复杂度，判定 10 秒内可完成就跳过 plan**。把这段原样设成 API 开发者指令后，5.5 xhigh 正确率 **10/10 → 2/10**；只删掉关键判断句，回到 **20/20**。

结论：让模型在开工前按时长/步数预判复杂度，会把它推进「简单问题快速回答」的短路分支。两个解法：prompt 前垫「不要把这个问题当作简单问题快速回答」，或发一张 1×1 透明 PNG（上下文含图片时该内置指令不插入，釜底抽薪）。

### 2. 可复现的分支对照：commentary 的有无 = 走哪条路

`openai/codex#29353`（2026-06-22，Codex Desktop，5.5 xhigh）用同一道糖果题开 5 个全新会话：

| phases | 答案 | reasoning tokens | 耗时 |
|---|---|---:|---:|
| `["final_answer"]` | 29（错） | 516 | 15.4s |
| `["final_answer"]` | 29（错） | 516 | 14.4s |
| `["commentary","final_answer"]` | 21 | 5884 | 114.0s |
| `["commentary","commentary","final_answer"]` | 21 | 3904 | 77.7s |
| `["commentary","final_answer"]` | 21 | 7766 | 145.2s |

中文 prompt 同样复现（29/516 ×2、21/3624）。**失败路径的特征是：没有 commentary、直接 final、恰好 516、十几秒收工**。注意 commentary 在这里是「是否进入完整推理分支」的**标志**，不一定是原因——这跟 haowang 那句 `DO NOT send optional commentary` 看似矛盾，其实一个在讲分支标志、一个在减少输出占用，社区自己也没统一。

### 3. 大规模统计：516 是 518 token 块的边界

`openai/codex#30364`：390,195 条响应记录、865 个会话、2026-02-01~06-27。

- exact-516 事件 3,363 次；GPT-5.5 只占 19.3% 的响应，却占 **82.0%** 的 exact-516 事件
- `exact-516 / >=516` 比率：gpt-5.5 **44.0%**，其他模型 1.3%（33.6 倍）
- 按月：Feb 0.11% → Mar 2.45% → Apr 4.25% → **May 53.30%** → Jun 35.84%；同期平均 reasoning tokens 从 268.1 掉到 106.9、P90 从 772 掉到 344
- 截断点是一串**等差数列**：516、1034、1552、2070、2588、3106、3624、4142、4660、5178、5696、6214、6732、7768，公差 **518**。也就是说预算按 518 token 一块切，任一块边界都可能被掐，不是只有 516

糖果题五连测（正确答案 21）更能说明问题：

| 模型 / effort | 五次结果 | 判定 |
|---|---|---|
| 5.6-sol / terra（high + xhigh） | 全 21，reasoning 2277~9840 | Fine |
| 5.5 high / xhigh | 全 516，4/5 错 | Affected |
| **5.6-luna high** | 29/516、21/2822、21/3017、29/1034、29/516 | **3/5 错** |
| 5.6-luna xhigh | 全 21，reasoning 4660~12622 | Fine |

**这一行很关键**：luna 在 high 下会落进 516 截断档，xhigh 下又正常。所以「服务端静默换模型」和「预算截断」不是并列的两型，可能叠加甚至同源——被路由到 luna 再叠加 low/high effort，就更容易踩中短路分支。

### 4. 中文社区复现与绕过

`router-for-me/CLIProxyAPI#3937`（[讨论] OpenAI 对第三方客户端发出的请求降智）：

- 对照：Codex CLI 直接登录不降智；Python Codex SDK / CLIProxyAPI / OpenCode 更容易降智；但长任务中直连也会 516
- 社区主流结论转向「**不是换弱模型，是推理链被强制截断**」，用户仍收到回复，只是由不完整推理链生成，表现为前后矛盾、尾部自修复
- 有回复明确写「**GPT-6-Astra 出现严重的 516 截断降智**」「5.6 sol xhigh 也出现 516」——所以这问题没被彻底修掉，只是随时间/账号/时段波动
- 统计口径：分母应为 `>=516`（复杂任务），有人算到 50%；Reddit 另一份统计是 30% 的请求 `>=516`、其中一半被提前截断
- 缓解：检测 516 就报错重试的 CPA 插件、`Tai-Wei/codex-516-fix`（一份防短路 AGENTS.md，README 于 10/19 标注「最新版本中已修复，存档」）、xhigh（概率更低但不保证）、纯净请求（不带工具、不用 Codex 自带系统提示词，能稳定得 21，但工程上做不到）、换旧版 5.2 系统提示词（个例）
- **无 OpenAI 官方回应**；`commentary`、`X-Codex-Turn-State`、伪装官方客户端/改 header 在这份讨论里都没有具体方案

### 5. 时间线：确实被官方悄悄改过

1701975 帖 384 楼（7/8）复测 250+ 次，5.5 Pro Extended 变成 0/110、3/69、0/70+，几乎不出错，发不发透明图都一样；`codex-516-fix` 10/19 标「已修复，存档」。但 #3937 里 6-astra 仍有人报 516。**结论是时好时坏、按版本和账号波动，不是一劳永逸修好，也不是一直存在**。你本机 11 月 0.5% 的数据站在「现在不严重」这一侧。

## 三、必须修正的两个旧判断

这两条是前两轮我下的，都错了，一并更正：

1. **糖果题 21 是对的，29 才是错的**。题目明确写了「形状靠手感可以分辨」，参赛者可以**按形状主动挑取**，不是纯随机盲抽。正解是取 9 个圆形（圆形西瓜只有 8 个，故必含一个圆形苹果或桃子）+ 12 个五角星形（必含星形桃子或苹果）= **21**。29 对应的是「只能决定总数、不能控制形状」的盲抽理解，恰恰是 516 短路路径漏掉可控条件后给出的错误答案。#29353、CLIProxyAPI#3937、`codex-516-fix` 三处一致。我之前那个穷举把题建错了模型。
2. **516 不是「模型在认真算、状态稳定」**，而是推理被固定阈值截断的指纹。上一轮把糖果题 issue #8 的五次 516 解读反了。

## 四、这份数据能证明什么、不能证明什么

| 问题 | 能否判定 | 依据 |
|---|---|---|
| 第三种（预算截断）现在是不是主因 | **基本排除** | 1405 次响应仅 7 次边界命中（0.5%），10 月底 368 次响应 0 命中 |
| 第二型（服务端静默换模型） | **测不了** | 本地 `turn_context.model` 是客户端设定值；11/03 单会话 20 次手动切换可证。要抓 `response.model` 或响应头 `x-codex-safety-buffering-faster-model` |

| 冷号方向对不对 | **没被推翻** | 第三种已排除，剩下两型都指向账号/路由层 |

一个反向提醒：如果冷号期间你根本没跑任务，日志里自然不会有「坏样本」。但 10/28–10/31 有 368 次响应且 0 命中，这个覆盖是有意义的，不是空窗。

## 五、下一步建议

1. **冷号继续**，别因为这篇把重心挪到改提示词上——本机数据不支持第三种是主因。
2. 冷号结束后要验「恢复没恢复」，最硬的判据是抓响应里的 `response.model` / `x-codex-safety-buffering-faster-model`，本地 rollout 日志里没有这两个字段，得在请求侧抓（上轮提过的脚本就是干这个的）。
3. 顺手可做的零成本检查：把 `model_reasoning_summary = "auto"` 加进 `~/.codex/config.toml`，让 UI 显示思考 summary；再跑固定 prompt × 5，看是否有「直接 final、十几秒收工、reasoning 卡在 516/1034/1552」的形态。有就说明第三种回来了，没有就不用管。
4. `codex_516_check.py` 可随时复跑，`zstandard` 已装在隔离环境 `~/.workbuddy/binaries/python/envs/default`。
