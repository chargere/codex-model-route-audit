## 三·补 · 封号风险（11/08 17:39 核查）

**结论：风险远低于社区里被封的那些场景，但不是零；最保守可跑「纯观测模式」。**

- **用的是官方支持的配置项。** v1.5.1 起项目不再用自定义 provider，而是保留内置 `openai` 身份 + `openai_base_url = "http://127.0.0.1:8787"`（官方配置文档列明的地址覆盖项；官方只要求它写在**用户级** `config.toml` 而非项目级，防的是陌生仓库把请求引到别处）。**纠正此前口误**：之前说的「加自定义 provider / `requires_openai_auth`」是旧版 `openai-retry` 做法。
- **官方风控点名的违规项，本地 relay 一条不沾**（蓝点网 / 官方支持文档口径）：Sub2Api 等反代站、多人共享账号 / 共享凭证、IP 频繁变化、低质量机房 IP、屡次越狱、滥用漏洞。本地 relay：无第三方服务器、无账号池、用你自己的 OAuth、出口 IP 不变、代码在本机可审、请求体与鉴权头字节透明转发。
- **作者自己怎么说**（README「安全吗」）：「我不能保证为零 —— 任何改变了请求时序的客户端都不属于默认行为」，但「**没有**做共享凭证、伪造客户端、绕过额度、逆向协议」。注意这句残余风险针对的是**重试**；我要加的只读 tap 不改请求、不改响应、不改时序，等于把这点也削掉。
- **更保守：纯观测模式。** 启用时把 `--max-attempts 1`（或直接关掉重试），relay 只做转发 + 记录，遇到 overload 原样透传。连「改变请求时序」都不存在。代价只是满载报错不再被自动吞掉——反正你跑的是 5 次鹈鹕测试，不是长任务。README 本身也建议「想更保守可以把 `--max-attempts` 调到 10，并把退避拉长」。
- **理论上仍存在的一点**：relay 用 Python 标准库发上游请求，TLS / HTTP 指纹与官方 Rust 客户端不完全一致。但 `openai_base_url` 本身就是官方接受的中间层配置，作者长期实测也未见封号报告。
- **真正该躲的不是 relay**：① 冷号期（现在 → **11/10 下午**）别启用，账号正在观察期，任何重连 / 请求都是活动；② 别高频探针、别并发、别用第三方检测站（社区有「探针过去号秒封了」的反馈）；③ 别在这时候换 IP（官方明确 IP 频繁变化会触发风控，你机房 IP 虽检测干净也别跳）；④ 只跑 5 次正常 prompt。
- README「局限」里作者自己写「响应里的 `served` 字段也可以打日志核对」—— 我要加的正是他想到但没做的那一段。
