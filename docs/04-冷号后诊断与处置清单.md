## 这次修订改了什么

用户补充「个人邮箱账号 + 机房 IP 但检测干净」之后，加上重新查证，前面两处判断要撤回：

1. **11/05 那三个 `x-codex-safety-buffering-*` 头不是降级证据。** 它是回退链资格声明，带链的健康响应都会带（测量报告原话 "declared on every healthy response"、"The headers only announce eligibility"）。真正坐实换模型的是 SSE 里 `response.model` 被改写，或 `openai-model` / `x-openai-model` 响应头不一致。
2. 11/05 那三行里没有 `openai-model` / `x-openai-model`，`primary-used-percent` 只有 0/1/2（社区说要到 100 才切 luna）。所以那三轮**没有降级证据**。
3. **【新增，非撤回】「别拿鹈鹕测试当判据」这条要改口径。** 成品「画得像不像」确实 noisy（`#44851` 作者自己标注），但**首段回复的措辞指纹**是社区公认的可用判据：11/07 23:44 那次命中了「内嵌 SVG」。详见 `output/内嵌SVG指纹核查报告.md`。

结论：**目前没有任何硬证据表明这个号被降级过**，更没有证据说它"脏"。体感降智是事实，成因完全没定位；行为层出现了一条可疑但自相矛盾的线索。

## 阶段 0 · 冷号期间（现在 → 满 24h）

**社区那套冷号组合拳对你基本不适用**，它的前置条件是「用了中转站 / 并发或额度消耗过快 / 账号被标记」：

- 你没用中转、号是自己的、IP 检测干净 → 「删中转账号 / 改密码 / 换干净 IP」这几步做了也是白做。
- 唯一还可能有点用的：静置让 7 天窗口滚过去（`secondary-window-minutes: 10080`，11/05 时 `secondary-used-percent: 24`），以及别在冷却期把 5 分钟 `primary` 打满。但这是推测，没有证据。
- 所以冷号可以继续，但**别把它当主力**，也别为了它折腾账号。少动、低并发（< 3）就行。
- 顺手做零成本的请求瘦身：开新会话、禁掉不用的插件 / MCP、压图片。作者实测 >500 KB 请求平均重试 6.75 次，其余约 1.7 次；长会话重发历史约 724 KB、新会话约 89 KB。这一条无论哪一型都该做。
- 顺手把个性化里的**「快速回答」关掉**：locdd 原帖说开着会严重干扰措辞判据，有人关掉后 APP/CLI/网页端降智短暂全部消失（过一阵又回来了）。零成本，复测前先关。

## 阶段 1 · 复测批次（冷号满 24h 后，一次性跑完）

**A2 · 零成本先跑（新增，不用改任何环境）**

1. 新会话，模型 `gpt-6-astra`，effort 拉到 **High / xhigh**，确认「快速回答」已关。
2. 原样发固定 prompt：`创建一个 HTML，内容是 SVG 绘制一个鹈鹕骑自行车的 2D 动画。`
3. **只看首段回复的词**，别看成品画得好不好：
   - `内嵌 SVG` / `内联 SVG` / `循环骑行` / `连续循环` / `为您生成了` → 记一次疑似
   - `踩踏` / `沿途风景` / `背景移动` → 记一次满血侧
   - 两组同时出现 → 记「混合」，必须复测
4. 连续 5 次，记录首段措辞、思考/总耗时、`reasoning_output_tokens`、成品行数。
5. 自动打标：`pelican_fingerprint_check.py --date 2026-11-09 --html "新生成的.html"`。
6. 判读：`循环` 命中 ≥1 次，或 `内嵌 SVG` 高频 → 第二型先验显著升高，**此时必须上 A 抓 `response.model` 才算坐实**。

**A · 唯一能确诊的是抓上游**（本机日志里根本没有 served-model 这个信号）：

- 首选：给已落地的 `codex-overload-fix/relay/relay.py` 加一段**只读记录**写到 `~/.codex/model_probe.log`。它本来就在解析 SSE，改动很小。要抓的字段：
  - `response.created.response.model` / `response.completed.response.model`（**真正的 swap 信号**）
  - 响应头 `openai-model` / `x-openai-model`（官方 `response_model()` 读的就是这俩）
  - `timing_metrics.engine_ids`（社区用 `gpt56lun` 之类判断实际引擎）
  - `x-codex-turn-state` 长度、`x-oai-request-id`、`x-codex-primary-used-percent`
  - `x-codex-safety-buffering-*`（**只当背景，别当判据**）
  - 注意：`scripts/install.ps1` 会改 `~/.codex/config.toml` 并写 HKCU 自启，之前一直没执行，等确认再动。
- 次选：mitmproxy + 自定义 CA 抓 `chatgpt.com/backend-api/codex`；或用现成的观测工具（如 `codex-state-kit` / `codex_state_monitor`，它们已经把 served-vs-requested 校验做好了）。
- 不建议：只靠 `logs_2.sqlite`，采样太稀，全库 `response.model` 0 行。

**固定 prompt × 5**（新会话、同一 effort=xhigh、别开插件）：
- 用有指纹的题（糖果题正解 21 / 24 点题 2578），或直接拿鹈鹕题，五次保持完全一致。
- 每次记录：`response.model`、`openai-model` / `x-openai-model`、`reasoning_output_tokens`、`output_tokens`、耗时、有没有 `commentary`、首段措辞。
- 复测前确认 effort 没被 UI 降到 low —— 11/08 00:53 最后两轮 astra 就从 xhigh 掉到 low 了，effort 掉了体感也会像降智，但那不是服务端换模型。

## 阶段 3 · 若确诊第二型（重新排序）

前提变了：账号和 IP 本来就干净，所以「换更干净的号 / 换更干净的 IP」的边际收益接近 0 —— 社区那些成功案例是「脏 IP / 中转号 → 干净」的改善，你已经在干净侧了；而且社区实测「降智跟 IP 大概率没有任何关系」。B.2 实测约 50 次探针也证实：**没有任何客户端开关能关掉回退链**（`x-codex-safety-buffering-enabled: false`、`service_tier`、`x-codex-routing-hint` 全无效），也没有 mid-turn escape。

1. **临时切 `gpt-6.1-sol` 保生产** —— 最实在。`#46189` 同账号同分钟 sol 12/12 正常；`#44851` 同 prompt 下 sol 产出 21.9 KB、astra 只有 5.8 KB。既然是服务端对 astra 的路由，绕开 astra 比修账号现实。
2. **低并发、压请求体积** —— 社区说「短时并发 / 额度消耗过快」会触顶，这条至少可控。
3. **向官方反馈** —— 带上提示词、对话 ID、模型档位、发生时间、`x-oai-request-id` 与首段措辞截图（PaperLab 建议 Help Center + `<REDACTED_EMAIL>` 两条都试）。
4. **换号 / 换 IP 碰运气** —— 继续下调。`#45925` 称失败率差约 7 倍、`#46189` 评论 3 说换 IP 能恢复，但那是账号被污染的场景；你现在换，等于把唯一干净的变量换掉，风险自己掂量。
5. **冷号 / 静置** —— 只剩「让 7 天 secondary 窗口滚过去」这条推测，别当主力。
6. **等官方** —— `#46189` 仍 open，官方只在一次更新里部分承认过 "badly configured engines… removed"，之后沉默，状态页一直 fully operational。
